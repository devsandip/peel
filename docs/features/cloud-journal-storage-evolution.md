## Current constraint and decision

The implemented [store](../../infra/cloud/journal-storage.ts) checks application_id0x53594a31 and user_version1 before SQL, then requires exactly the one fixed journal_genesis table and original immutable genesis. Adding intent/fence/state/observation tables to that catalog is a format change. The [file boundary](../../infra/cloud/journal-files.ts) checks selected physical ownership/identity/bounds and exposes header bytes; the storage layer owns logical version/catalog checks. It is not correct to describe the file helper itself as a schema-version validator.

Keep v1 a recognized genesis-only format. Its existing APIs, bytes, errors, scope/marker/storage identifiers and conservative session behavior stay intact. Choose a separately fixed fresh-v2 storage/initializer path for later immutable writes. Retain the application family identifier and compatible original genesis/derived location; user_version2 distinguishes the new fixed catalog. Reserve that version now as a design decision, not a claim that a v2 implementation or compatible database exists. The implementation plan must freeze the complete exact v2 DDL, constraints/indexes/triggers and bounded codec catalog before writing code. Once implemented, additional catalog elements require an explicit reviewed format transition, never a permissive extra-table check.

| Selected state                                        | Allowed behavior                                                                                                                                   | Forbidden inference/action                                                                          |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Recognized v1                                         | Existing original-source/genesis validation and historical inspection                                                                              | No v2 prepare/fence path, implicit upgrade, ALTER/repair/reset or session upcast                    |
| Genuinely absent selected workspace/journal           | Future fixed v2 initializer may obtain its own exclusive workspace, actual reserve/source/bootstrap acknowledgements under all original controls   | Absence does not itself establish current provider readiness, permission or an unused global budget |
| Recognized v2                                         | Future exact-v2 reader validates its entire protected catalog/state; only its original fresh process may later prepare after separate actual gates | Rows, version flags, copied/read/reopened metadata or another process never restore creation        |
| Unknown/partial/conflicting version/catalog/namespace | Preserve and refuse; explicit metadata inspection only when that exact format is supported                                                         | No fallback to a looser reader/writer, sibling database, discovery scan, migration or replacement   |

There is no in-place v1-to-v2 migration in this policy. An existing v1 workspace, including an empty or stranded selected initialization, remains preserved. Do not reuse its reservation, reserve again, refund, restamp, reset or switch paths to continue the failed/legacy run. Any genuinely later run still needs fresh independent authorization/source/account/region/cost/budget/cleanup controls and the actual funding ledger's normal slot/cleanup rules. Local storage evolution grants none of those. This conservative choice can strand a legacy workspace; it preserves the existing no-restart-creation policy rather than inventing migration authority.

## Fixed initialization and read-only routing

The later implementation must provide an explicit compiled v2 initializer/store/facade path, with no public version/schema/codec/store callback override. Keep the current v1 initializer unchanged. Share proven internal mechanics only through a separately reviewed compatibility-preserving extraction when needed; do not duplicate the whole initializer or weaken its actual acknowledgement barriers. A caller version field or a v1 session/read result cannot mint v2 lineage.

The fixed v2 initializer must itself capture strict original inputs before path access, require the selected workspace/journal to be genuinely absent, acknowledge exclusive private workspace before its own actual reservation, publish the original sources and obtain their separate sync acknowledgements, bootstrap the exact v2 schema/original genesis, synchronize/read back all recognized files and close descriptors before entering private live state. Preserve the actual funding/source/parent/workspace identities. Failure/uncertain commit/lost ACK leaves preserved state and no fresh lineage, with no adoption/read fallback. This adds no private current provider assessment or execution grant.

A future metadata-only recovery dispatcher may recognize version1 and version2 explicitly after the same independent anchor/physical/header checks. It delegates to their separate exact readers. It must not initialize, upgrade, change header/marker/schema, normalize an unknown catalog, select a different path or return any live preparation/session/send capability. Missing source sync, expired original quotes/leases, process loss and restored snapshots remain creation refusals. Otherwise authorized, independently proven-owned cleanup retains its separate route; an unknown journal is not ownership proof or a false durable receipt.

Keep the original format1 genesis JSON immutable, including its original revision0. A separate v2 state revision records actual later journal mutations. Genesis revision0 never proves absence of pending intent/fence or an unsent operation. Validate v2 revision/rows/references/counts coherently under the exact catalog and independently selected original scope. Never persist a fresh-process/readiness/owned/send permission flag. The future live coordinator must retain version-specific acknowledged lineage and current revision privately; copy/JSON/reopen/regression/uncertainty cannot recreate it.

## Bounded future state and capacity evidence

The exact v2 implementation plan must cover the existing protocol's four immutable intents, four dispatch fences, safe request projections up to16KiB, at most96 observations up to2KiB each (64ordinary and32reserved for cleanup), and complete bounded teardown facts/root. No column may checkpoint NoEcho/key/full request bodies, signatures/credentials, raw responses/event properties/parameter values or unrestricted reasons. The original full unsigned commitment is opaque and includes transient material; a separate key hash is not added. A teardown root must link validated per-resource facts and the complete original inventory, not an opaque digest/owned Boolean alone.

Keep the current2MiB database/4MiB recognized rollback-journal bounds and fixed SQLite settings unless a separate reviewed change proves they are insufficient. Arithmetic over logical limits is not physical SQLite capacity or a cleanup-reserve guarantee. Before a v2 runtime feature claims its bounds, measure fresh synthetic maximal records/catalog/index/transaction overhead, actual page count/byte bounds and rollback growth. Prove that ordinary state cannot consume the reserved cleanup capacity. Refuse growth or incomplete evidence, rather than silently raising limits. No actual/default operator/note database is opened for this work.

Later mutation slices still need actual BEGIN IMMEDIATE/uniqueness/revision/commit/readback/file-sync/descriptor-close/lost-ACK/process-race/SIGKILL evidence. Token/key/request capture belongs only in a winning future preparation transaction after actual private current gates; network IO stays outside SQL transactions. An acknowledged fence may later yield one private one-use send capability, never a restored row-derived one. Empty v2 tables, successful bootstrap, supplied response integrity and local schema checks do not prove provider ownership, adequate phase runway, managed success or teardown.
