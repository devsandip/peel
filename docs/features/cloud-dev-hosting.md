# Controlled Cloud development hosting

## Purpose and PR boundaries

[Issue 26](https://github.com/devsandip/peel/issues/26) plans [M2.2](https://github.com/devsandip/peel/milestone/2), a managed-service prerequisite for SPEC FR-04/14/20 and AC-04/12/13. It follows the [composed local evidence](cloud-foundations-evidence.md). This document authorizes no deployment by itself. Version 0.7 product scope and mockups remain unchanged.

Use a private invocation experiment first: a packaged Lambda, real DynamoDB and real Cognito-issued user tokens. Only the verified operator can invoke the Lambda through the IAM-authorized AWS API. Create no API Gateway, function URL, public app, event source, CloudFront distribution, relay or customer subscription in this slice. Cognito's managed sign-in domain is reachable publicly, but self-registration is disabled and only two generated fixture users exist.

This staging choice limits untrusted request spending. API Gateway throttles are [best-effort targets](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-throttling.html), not spending ceilings. Supplying HTTP payload-v2 envelopes to Lambda Invoke exercises managed identity, IAM and data; it does **not** prove API Gateway routing, proxy/header behavior, browser CORS, system-browser callbacks, app sign-in, live delivery or public acceptance. Those remain required M2 work. Do not represent the private experiment as a deployed HTTP API.

## Runtime, identity and data

- Package a deterministic ZIP with an explicit exported handler, bundled pinned SDK/verifier dependencies and no source maps, fixture tokens, environment files, credentials or note databases. Select **nodejs24.x**, x86_64, 256 MiB, 30-second function timeout and 512 MiB temporary storage. AWS lists Node 24 as supported and Node 26 as preview; [include the SDK dependencies](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtimes.html) rather than relying on the runtime's changing copy. Check the actual bundle under Node 24 separately from existing Node 26 development CI.
- Validate all environment values before constructing clients: exact table, region, pool/client/scope, HTTPS synthetic service origin, stable 256-bit cursor key and absolute development expiry. No default table, local endpoint, test identity bypass or inferred owner/paid flag. Lease expiry or initialization failure returns a fixed private no-store error before data access. This development fence does not replace production key rotation or token revocation.
- Use one Standard/on-demand DynamoDB table with the existing PK/SK contract, encryption, expendable-item TTL and no streams, secondary indexes, replicas, backups or PITR. Avoid retained synthetic backups in this short experiment. Production backup/restore remains a release gate. Bound fixture content to two owners, eight note IDs each and 1 KiB bodies. The table is not a free-mode note store.
- Use one explicitly selected Cognito Essentials pool, public client without a secret, authorization-code/S256 flow, `openid` and one custom sync scope. Disable self-registration, MFA/SMS, analytics, M2M/client credentials and real delivery. Admin-create at most two generated users with `MessageAction: SUPPRESS`, no real email/phone attributes and no aliases; set generated passwords privately. The default admin-create action can send an invitation, so [suppression is mandatory](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminCreateUser.html).
- Register one exact HTTPS fixture callback under the reserved `.example` domain. A fresh Chromium context intercepts that exact callback before network resolution, without disabling TLS validation to Cognito. The existing private PKCE initiator validates state/code/verifier/nonce; the exchanger validates real ID/access tokens against the pinned pool/client and nonce. The callback transport is synthetic. Cognito's [registered callbacks and code-flow options](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-cognito-userpoolclient.html) and [custom scope contract](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-define-resource-servers.html) remain enforced. Never replace the required scope with a direct password-auth shortcut.
- Only after validating both subjects may the operator seed synthetic server-side paid-policy metadata for their isolated libraries. This is a fixture policy, not a purchased subscription or app Cloud activation. Account isolation, revision conditions, replay/pagination and private authorization failures use the existing data routes and real managed storage.
- Generate a cursor secret in Secrets Manager, resolve it into the function's encrypted environment and import a nonextractable HMAC key. Never return it in outputs, logs, artifacts or reports. Store the ZIP only in an owned private encrypted S3 bucket with public access blocked; S3 contains no notes. The Lambda role gets only the required operations on this exact table. No execution-role log-write permission, request logging, tracing, log subscription or credential output is allowed in this probe. Operator evidence consists of booleans, counts and source/artifact hashes.

Existing account-level audit configuration is preserved and must be checked for additional enabled data-event charges before apply.

Set an operational allowance of **USD 2 per run**, at most **two runs**, plus **USD 1 reserved for cleanup**, so the total overnight experiment envelope is **USD 5**. Track consumed run slots privately before create; a failed/unknown create consumes its slot. Recalculate from fresh official rates within 24 hours of apply and reject a forecast above USD 2. The table's rate allowances exceed the tiny fixture, but the guard review must still check maximum route/SDK retry amplification against them. Use at most 64 sequential synchronous invokes, bounded SDK timeouts/retries, no automatic asynchronous retry source and no open ingestion path. Do not increase limits to make a failed probe pass.

Budgets/alerts and throttles cannot guarantee an instantaneous dollar stop. Do not change account-global billing/security settings or send budget notifications overnight. The controls are closed invocation access, bounded users/workload, a short lease, independent deletion and verified cleanup. If the deletion path cannot be made safe, do not provision. Lost cleanup could leave roughly USD 0.43/month of modeled secret/table/artifact storage at the stated bounds, plus any unverified provider residue; this is a cleanup failure, not permission for indefinite hosting. Actual billing can arrive late and remains unverified until reconciled.

## Lease, ownership and cleanup gates

1. Default tooling only plans/validates. Apply requires an explicit flag, a clean merged public-repository commit with passing artifact/protocol/IaC/guard checks, source and ZIP digests, and a private fresh plan. No agent-created account identity, token, code, password, subject, ARN or resource address enters public evidence.
2. Reverify the expected account using STS and the intended existing SSO profile immediately before writes; compare with a private expected-account record, pin us-east-1 and verify sufficient credential lifetime. Refuse account/region drift, unknown resources, stale quotes/plans, extra services, broad IAM, retained data, public ingress or changed source. Authentication alone is not provisioning readiness.
3. Use unpredictable run names and ownership tags, a private mode-0600 journal written before the first create, and exact stack/resource IDs after discovery. Guard infrastructure and its cleanup authority must exist before data/function resources. A failed checkpoint cannot skip cleanup; an uncertain create response requires ownership discovery, not assuming absence or issuing another blind create.
4. Limit each run to 90 minutes from the first write. Stop test calls at least 30 minutes before expiry; at/after expiry the handler rejects new work. Start only when the remaining authorization window and SSO lifetime cover the entire run plus a further 30-minute cleanup margin. For this overnight authorization, all work and cleanup must end before 09:00 Asia/Kolkata on 28 October. Do not shorten cleanup headroom to fit a late start.
5. Arm an independent one-time Scheduler cleanup before accepting data, with an execution role trusted only by this account and dedicated [schedule group](https://docs.aws.amazon.com/scheduler/latest/UserGuide/cross-service-confused-deputy-prevention.html). Use the [universal DeleteStack target](https://docs.aws.amazon.com/scheduler/latest/UserGuide/managing-targets-universal.html) against the exact data/function stack and a dedicated CloudFormation deletion role confined to its resource inventory. No public-invoke role or account-wide deletion rights. Keep the cleanup authority outside the stack it deletes; prove ownership and permission dependencies without circular deletion. The owned artifact bucket must be empty before it can be deleted. A separate guard stack can persist until the runner confirms data teardown, then must also be removed.
6. Tests must cover missing/late/disabled schedules, wrong trust or target, credential expiry, partial create, interruption, cleanup errors, unknown resources, nonempty/foreign artifact objects, stale source/lease/budget and a lost create response. Before managed note tests, verify the independent cleanup path on an owned empty sentinel stack, then arm and read back the actual target. Configured schedule state alone is not evidence that deletion works. If that rehearsal fails, stop and clean up without a data probe.
7. The runner's `finally` empties only proven-owned artifact objects, deletes the exact owned data/function stack, waits for settlement and independently verifies table, pool/domain, function, secret, artifact objects/bucket, schedules and roles are absent or explicitly in a documented provider deletion state. Then remove the guard resources. Do not use forced/retained-stack shortcuts, shared-resource edits or broad tag-based bulk deletion. Normal CloudFormation deletion of the newly generated disposable secret uses [ForceDeleteWithoutRecovery](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-attribute-deletionpolicy.html); actual removal is asynchronous. Deleted Cognito pools become invisible/inoperable but [remain inactive for 14 days before final cleanup begins](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_DeleteUserPool.html). Record those provider states honestly, without claiming immediate physical erasure. A successful DeleteStack request only [starts deletion](https://docs.aws.amazon.com/AWSCloudFormation/latest/APIReference/API_DeleteStack.html); it does not establish teardown.
8. No live run until every prior PR is merged, current account/cost/lease/permissions checks pass and cleanup rehearsal is possible. Stop after two controlled attempts; do not rerun a failed component blindly. Any unknown charge/resource or unmet test keeps issue 31 and the milestone open, with the exact remaining work. Preserve evidence privately and report only sanitized facts.
