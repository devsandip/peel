## Scope and supported state

Add `infra/cloud/journal-v2-catalog.ts` as a passive frozen compiled descriptor: format1, kind `synkies-cloud-journal-v2-catalog`, applicationId0x53594a31, userVersion2, pageSize4096, maxPages512, databaseLimit2097152, rollbackLimit4194304, observationJsonLimit1984 and the exact DDL below. Export no database/path/version/schema/callback input, execution function, reader/writer/initializer, session or permit. Importing it opens no file/database/process/network, draws no randomness and reads no clock. Future fixed stores must select the compiled descriptor internally; a copied descriptor grants no authority.

All future tables are frozen now, but no nonempty intent/fence/observation/teardown row codec or mutation API is implemented. The existing original format1 genesis codec and an eventual separate initial-state reader are the only current interpretation boundary; that future reader must require revision0 and all future tables empty until separately scoped compiled codecs/mutators exist. SQL-valid capacity padding is deliberately not a valid domain/provenance record. There is no generic JSON acceptance or caller codec registration. Later payload support needs explicit versioned closed codec review without silently changing this SQL catalog. Actual protected v2 namespace/bootstrap/acknowledgement/session and actual current/provider gates remain separate.

Request JSON is the safe16KiB projection, never the full unsigned body/key. Intent JSON is at most4KiB. Observation and teardown JSON use1984bytes, reserving64bytes within the2KiB row ceiling for SQL identity/category/revision/record overhead. Do not store duplicate hash/kind columns for observation JSON: its closed versioned payload identifies its kind and its hash can be computed over exact bytes for proof links. A future teardown payload must bind the complete original inventory and validated resource facts. This packing budget is a design hypothesis until actual Node24 page/rollback/cleanup measurements pass; it is not a promise from logical arithmetic. No limit is raised silently.

The state counter is mutable only by +1 with a fixed id; all other rows are append-only. Duplicate-insert guards also block REPLACE/IGNORE paths before unique conflicts. [SQLite conflict handling](https://www.sqlite.org/lang_conflict.html) and [trigger behavior](https://www.sqlite.org/lang_createtrigger.html), rechecked29October2026, require attention to replacement deletions and trigger error handling. Do not rely only on DELETE triggers or recursive_triggers being enabled. Tests must demonstrate these exact statements on actual Node24 SQLite. [SQLite limits](https://www.sqlite.org/limits.html) describe engine bounds; they do not certify this catalog's physical capacity.

## Pre-release review refinement: append identity and page geometry

The first artifact candidate/SQL tests passed, including maximal ascending insertion at465pages. A further actual Node24 in-memory review probe kept the same SQL-valid byte/count envelopes but varied insertion order: descending used507pages and deterministic shuffled used470, versus ascending465, all still within512. These are measurements of the first candidate, not universal capacity proof. Page geometry materially affects the remaining margin.

Before updating the artifact, this plan now explicitly requires observation_id1 followed by exactly prior maximum+1 for every append, across both categories. This matches an ordered append journal, prevents sparse/backfill/reverse insertion from consuming a different physical layout, and is enforced in the compiled INSERT guard linked above. Future writers assign the next ID only inside their winning transaction, with no caller-controlled backfill. Add a direct refusal case for gaps/reordering. This is a pre-release candidate refinement: no v2 store/namespace or actual operator database exists, no migration occurs and no byte/count/budget limit increases. Regenerate the independent golden from this committed revised plan before changing the TypeScript artifact, retaining first-candidate evidence separately; rerun final measurements/checks on the new catalog.
