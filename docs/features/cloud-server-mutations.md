# Conditional Cloud server writes and retry receipts

## Requirements and plan

FR-04/13/14/18/20 and AC-09/10/12/13/22/23 require account-scoped conditional writes, durable retry outcomes, paid access and body-free change hints. Implement the server service against an isolated transactional SQLite adapter before DynamoDB or application integration.

1. Accept a versioned collection/mode-generation envelope and immutable mutation. Receive the caller subject only from the future trusted authentication adapter, never from request JSON. Read current account status and entitlement from server records on every attempt and include their revision in the commit condition.
2. Recompute the mutation hash, enforce collection identity, body/item bounds and conditional base revision, then atomically update the note or permanent tombstone, account sequence, compact change and operation receipt. Retry sequence/policy contention; return an explicit conflict for note revision mismatch. Never use device time to choose a winner.
3. Keep operation receipts body-free for 90 days. A replay returns its original applied/conflict classification and original revision/sequence plus the latest current head. Do not retain a second note body in an operation record or return an old body after purge. Reusing an operation ID with another hash, note or mode generation rejects.
4. Use server time for Trash entry and its 30-day deadline. Editing a trashed note cannot extend retention. Materialize an expired note as a permanent tombstone and compact change before serving it or processing restoration. Expired operation receipts are logically expired even before physical cleanup. Keep deletion markers indefinitely in this prototype.
5. Exercise actual SQLite rollback/reopen, concurrent same-note and different-note writes, policy revocation during a held commit, two owner contexts, lost-response retries, stale/altered operations, retention and permanent purge. Connect two durable local clients to the service in a synthetic integration fixture and verify acknowledgement, repeated conflicts and restart.
6. Add a bounded HTTP adapter with an injected authentication resolver and a strict portable response adapter. Verify two durable clients over a loopback Node server using synthetic authentication. A replayed receipt whose current head has advanced must preserve local work and request reconciliation rather than falsely acknowledge the current note.

## Decisions and limits

The service receives a caller subject from an injected authentication resolver. Loopback tests use synthetic authentication; no Cognito verifier or hosted endpoint is enabled. SQLite account/entitlement setup is a fixture administration surface, never a client request flag. No billing, AWS deployment or real note data is used. Actual DynamoDB transactions, production authentication, quotas, cursor/push delivery and public account-deletion completion remain gates.

Operation receipts carry no snapshots. Responses pair a stable receipt with the latest server head; clients must inspect head revision and purge state rather than treating a replayed receipt as the latest note. This avoids keeping deleted text in retry records. Conditional purge of a never-created ID may create a revision-one tombstone; a purged identity accepts no further upsert.

## Evidence

`CloudMutationService` now verifies immutable hashes and current collection/mode scope, then conditionally commits the note or tombstone, account sequence, compact change and body-free receipt. The isolated SQLite adapter includes current account/entitlement revision and note revision in the same transaction. A competing policy revocation defeats the write. Missing account, inactive entitlement and deleted identity fail; request JSON cannot select an owner or grant paid access. Fixture administration is separate from the HTTP handler.

`createCloudMutationHandler` resolves the injected identity before reading a bounded JSON body, exposes POST mutation and GET note routes, and returns private error codes without internal exceptions or payload logs. `planCloudServerReply` and `applyCloudServerReply` apply an ordinary acknowledgement/conflict to the durable local repository. The subsequent [per-note head reconciliation](cloud-head-reconciliation.md) now retires an exactly matched accepted operation, adopting a newer head for a clean client or preserving a later local draft as a conflict. Missing-head conflicts still require a resnapshot decision.

The [initial synthetic report](../experiments/cloud-server-mutations-2026-10-27.json) records 12 passing server/HTTP cases and all 102 shared top-level cases, with TypeScript and formatting passing. They cover conditional and concurrent writes, rollback/reopen, immutable/reused/expired operation IDs, two owner contexts, scope and request-authority rejection, revocation before commit, server Trash deadlines including failed cleanup, permanent tombstones, malformed schemas, bounded HTTP input and private errors. Two durable local clients exchange real loopback HTTP requests, preserve both offline branches through repeated 409s, explicitly merge, restart after a lost acknowledgement and retry the identical operation. Newer-head recovery was completed in the linked subsequent feature and report.

Three actual subprocess SIGKILL checks pass after a committed write and inside uncommitted update/purge transactions. Reopening preserves the previous whole note, sequence, receipt and change state. The same retry succeeds without duplicate sequence advancement; an acknowledged purge leaves a body-free permanent head. These are Node SQLite boundaries, not DynamoDB or physical power-loss measurements.

No application database, real note, account token, hosted resource, subscription or running app was used. Synthetic authentication is not Cognito or production account-security evidence. DynamoDB encoding/transactions, production native/web authentication, CSRF/origin policy, quotas, paginated pull/cursor commits, push, full bootstrap, mode migration and public account deletion still need implementation and acceptance. The SQL fixture's deleted-account status blocks access but does not implement account-content erasure. Scheduled cleanup, including lapsed subscriptions, remains open. Old SQLite/WAL pages are not claimed securely erased.

The M0 service uses a conservative 400 KiB JSON-record budget alongside the 256 KiB UTF-8 body limit and a 2 MiB HTTP request bound. This is not DynamoDB's actual attribute encoding measurement and must be resolved before selecting production item validation. No public acceptance criterion is complete from this result.
