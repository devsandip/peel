# Durable current trust for direct peer operations

## Requirements and plan

FR-13/14/17/19 and AC-03/09/12/13/21 require authenticated paired devices, replay rejection, revocation and durable acknowledgements. The existing bound harness verifies an in-memory registry before a separate session claim. Close that ordering gap in the isolated M0 store before app integration.

1. Persist only explicitly confirmed public identities in the same compare-and-swap store as notes and replay claims. Keep a monotonically increasing per-device trust generation on confirmation or revocation. A received key/proof cannot create trust. Reconfirmation invalidates old sessions. Retain revoked records so an old generation cannot return after deletion.
2. Verify the signature against the locally reconstructed transcript and current stored key inside a retried transaction. Commit the consumed local challenge, session claim and trust generation atomically. Mint only an in-memory opaque session handle after that commit. Stored claims cannot restore active handles after restart.
3. Route direct-author edit, purge and acknowledgement operations through a scoped store. Validate the handle, current trust generation, stored claim and expiry on reads and before compare-and-swap commits. A committed revocation before a note commit forces retry and rejection; a completed note commit before revocation remains valid. Closing a handle rejects later commits. No third-party forwarding is added.
4. Raise the logical identity version so older experiment engines refuse the changed authorization state. Preserve clock-independent local drafts. Exercise both real SQLite and IndexedDB: failure/retry, reopen/replay, forged or foreign handles, re-confirmation, expiry, revocation while authorization is pending and revocation/closure while a note mutation is pending.
5. Compose the scoped operations with the bound channel fixture only after the shared contracts pass. Record actual checks separately from pairing UX, native Keychain, cross-network transport and public acceptance.

## Decisions and limits

This is an isolated direct-peer prerequisite. Public keys are not secrets, but reports still contain only booleans and counters. The legacy reducer and DurableReplica methods remain lower-level authenticated-input fixtures; production callers must not use them as an authorization boundary. The new scoped path must not trust a caller-supplied author set or peer ID.

Trust is local to this replica. Pairing confirmation UI, trust propagation, a device directory, clock repair, full-duplex readiness/credits, durable bounded inventory and native/iPhone storage remain open. Expiry is checked during the local operation, while compare-and-swap orders competing durable mutations. Immediate remote disconnect is a session-manager responsibility; current-trust commit checks prevent a disconnected or stale session from authorizing later durable writes. A mutation already committed before revocation remains valid. An operation authorized before in-memory closure can finish unless the durable closure wins the compare-and-swap ordering. No app integration or acceptance claim follows from this plan.

The logical identity is now version 3 and accepts versions 1/2 as upgrade inputs; the generic adapter layout stays version 1. Trust records, including revoked generations, have a provisional fail-closed capacity of 64. Replay retains the existing 4,096-claim capacity and monotonic time floor without pruning. These are M0 safety bounds, not public pairing/session quotas or a completed long-term cleanup policy. Lower-level DurableReplica authenticated-input methods remain available to reducer fixtures and cannot substitute for the scoped authorization path.

## Evidence

TrustedReplica stores confirmed public keys and monotonic generations beside note/replay records. It verifies the current key and locally reconstructed transcript before atomically claiming a challenge, then issues an immutable instance-local handle held in a WeakMap. Scoped direct edit/purge/ack operations recheck durable trust and claims before compare-and-swap. A competing committed revocation/closure changes the revision and causes the stale operation to retry and reject. Stored claims and copied handles cannot activate another instance.

Ten shared contract scenarios pass on actual Node 26.4 / SQLite 3.53.2 and Chrome 156 IndexedDB. They cover explicit pairing/key mismatch, altered proofs without challenge consumption, claim rollback/retry, restart/replay, copied/foreign handles, direct authorship, peer-scoped acknowledgements, purge, reconfirmation, expiry/closure, malformed counters/replay records, substituted keys and held authorization/edit/purge/acknowledgement/closure races. Local drafts still commit while peer authorization is unavailable. TypeScript, formatting and all 67 shared cases pass. The existing eleven-store-scenario contract, four SQLite SIGKILL boundaries and browser draft/projection reload also pass. [Store metadata](../experiments/peer-current-trust-2026-10-27.json).

The same-page bound Chrome 156 harness now uses durable confirmed trust and scoped operations. All 16 checks across twelve fresh host/host DTLS sessions pass, including installed-description proofs, 252,026-byte Unicode delivery, commit-before-ack, failed/quarantined receipt, lost ack/reopen/retry, purge, active/pending revocation malformed/early/forwarded traffic and an independent durable revocation blocking outgoing frames. Sending rechecks current trust after any buffer-drain wait and before each frame is handed to transport. Previously authorized/sent bytes cannot be recalled. [Composition metadata](../experiments/bound-current-trust-2026-10-27.json). These checks do not establish remote relay, native/iPhone, pairing UX, clock repair, production keystores or full acceptance. The native WebKit and disposable relay failures remain separate stopped gates.
